# Очередь задач и учёт запросов — инструкция по внедрению

Ветка: `feature/job-queue` → `main`.

## 1. Что сделано

| Задача | Решение |
|---|---|
| Много моделей, запросы из разных проектов | Каждый запрос к модели — **задача** в SQLite `data/ai_manager.db`: проект, модель, вид, статус, время постановки/старта/окончания, ошибка, токены |
| Отметка о выполнении / отмене | Статусы `queued → running → done / failed / cancelled / timeout`, `queued → expired / cancelled` |
| Отмена долгих задач | Лимит ожидания в очереди `AIM_JOB_WAIT_TIMEOUT` и лимит выполнения `AIM_JOB_RUN_TIMEOUT` (по умолчанию по 60 мин); клиент может задать свои — заголовки `X-Job-Wait-Timeout` / `X-Job-Timeout` |
| Очередь к одной ИИ | Планировщик `app/jobs.py`: задачи к текущей модели выполняются по порядку (до `parallel` одновременно) |
| Запрет переключения при наличии задач | Модель переключается **только** когда по ней нет ни выполняющихся, ни ожидающих задач. Ручной `start`/`stop` → `409 model_busy`; `restart` → `409 queue_busy` |

Новые файлы:

- `app/jobs.py` — `JobStore` (SQLite) и `JobQueue` (планировщик, таймауты, отмена, восстановление после рестарта);
- `app/executors.py` — как выполнить чат (обычный и стрим) / картинку / речь на запущенной модели;
- `app/queue_api.py` — эндпоинты `/api/queue`, `/api/jobs*`, общие хелперы (проект, таймауты, ошибки);
- `tests/queue_smoke.py` — смоук-тест без GPU (фейковые модели, отдельный порт 8799).

Изменено: `main.py` (эндпоинты идут через очередь), `openai_proxy.py` (то же для `/v1`),
`schemas.py` (поле `model` в `/api/chat|image|tts`, поля очереди в `/api/status`),
`README.md`, `SPEC.md` (раздел 4.5, инварианты I5–I6), `.env.example`, `.gitignore` (`data/`).

### Как работает планировщик

```
запрос ──► resolve_model ──► задача queued (БД) ──► ждёт слот ──► running: запуск модели (если нужно)
                                                                   └─► выполнение ──► done/failed/timeout/cancelled
Выбор следующей задачи:
  1) GPU занят моделью X → добираем задачи к X до parallel;
  2) GPU свободен, есть задачи к активной модели → берём их (не переключаемся);
  3) иначе → самая старая задача к другой модели → переключение.
```

- Без поля `model` запрос идёт на текущую модель подходящего типа (как раньше).
- Неизвестное имя модели в `/v1` (IDE шлют `gpt-4o` и т.п.) игнорируется — как раньше.
- Упавший llama-server перезапускается, когда до задачи дойдёт очередь (как раньше).
- Стрим: таймаут, отмена через API или обрыв клиентом закрывают соединение с llama-server —
  генерация останавливается сразу.
- OpenVINO (картинки) и llama-tts (речь) прервать нельзя: клиент сразу получает `504`,
  но следующая задача начнётся только когда поток реально закончит.
- После рестарта сервиса: ожидавшие async-задачи (`POST /api/jobs`) ставятся заново,
  остальные незавершённые помечаются `failed`.

## 3. Что сделать утром (по порядку)

### 3.1 Проверить на живых моделях

1. Остановите рабочий сервис (окно `run.bat` / задача «AI-Manager») и убедитесь, что активна
   ветка `feature/job-queue`. ⚠ `run.bat` при падении перезапускает сервис из этой папки — то есть
   с кодом той ветки, которая сейчас активна.
2. Прогоните смоук-тест (GPU не нужна):

```bash
venv\Scripts\python -m tests.queue_smoke
```

3. Запустите `scripts\run.bat`. В `.env` ничего добавлять не обязательно (значения по умолчанию
   = 60 мин); при желании скопируйте блок «Очередь задач» из `.env.example`.
4. Проверка очереди вручную (пароль из `.env`):

```bash
curl -H "X-API-Password: 12345" localhost:8000/api/queue
```

5. Сценарий конфликта: в одном окне запустите долгий запрос к `gpt-oss-20b`, в другом сразу —
   к `qwen36-35b-a3b`; в третьем — `GET /api/queue`. Ожидается: второй ждёт (`waiting`),
   `switch_locked: true`, `POST /api/models/qwen36-35b-a3b/start` → 409. После первого —
   переключение и выполнение второго.

```bash
curl -X POST -H "X-API-Password: 12345" -H "X-Project: test-a" -H "Content-Type: application/json" -d "{\"model\":\"gpt-oss-20b\",\"messages\":[{\"role\":\"user\",\"content\":\"Напиши длинный рассказ\"}]}" localhost:8000/v1/chat/completions
```

```bash
curl -X POST -H "X-API-Password: 12345" -H "X-Project: test-b" -H "Content-Type: application/json" -d "{\"model\":\"qwen36-35b-a3b\",\"messages\":[{\"role\":\"user\",\"content\":\"Привет\"}]}" localhost:8000/api/chat
```

6. Проверьте Continue в VS Code (стрим через `/v1`) и local_code_worker — должны работать как раньше.
7. История: `GET /api/jobs?limit=20`, сводка: `GET /api/jobs/stats?hours=24`.

### 3.2 Клиенты

Старые клиенты сначала вызывали `POST /api/models/{name}/start`, затем слали запрос без `model`.
С очередью это ломается при конкуренции: `start` вернёт `409 model_busy`, а запрос без `model`
может уйти на чужую модель. Правильно — **указывать `model` в каждом запросе и не вызывать
start/stop**: очередь сама запустит модель, когда подойдёт её очередь.

Клиенты доработаны отдельными PR:

- **auto_posting** — [Vasiliy-Blokhin/auto_posting#2](https://github.com/Vasiliy-Blokhin/auto_posting/pull/2):
  `model` и `X-Project` в каждом запросе, без ручного `start`; `stop_all` не считает 409 ошибкой;
  `503 expired` → `AIUnavailable` без повторов, `504 timeout` не повторяется.
  **Сливать после этого PR** — старый AI Manager не запускает модель по полю `model`.
- **local_code_worker** — [Vasiliy-Blokhin/local_code_worker#2](https://github.com/Vasiliy-Blokhin/local_code_worker/pull/2):
  `X-Project`, индикатор «GPU занята» в UI, 409 на ручной запуск вместо 502, ошибки очереди
  в стриме не повторяются. Совместим и со старым AI Manager.

Агентная сессия local_code_worker = много коротких запросов, каждый — отдельная задача. Между
запросами агента модель **может** переключиться на чужую задачу (если та ждала) — это ожидаемо;
кэш промпта llama-server после переключения теряется. См. 4.1.

**Continue (VS Code)**: в `~/.continue/config.yaml` можно добавить проект:

```yaml
requestOptions:
  headers:
    X-Project: continue
```

## 4. Что можно доработать дальше

1. **Удержание модели за сессией агента.** Сейчас приоритет — у текущей модели, пока у неё есть
   задачи *в очереди*. Между шагами агента очередь на мгновение пустеет, и задача к другой модели
   может перехватить GPU. Вариант: «аренда» модели — после задачи держать модель ещё N секунд
   (`AIM_MODEL_HOLD_SEC`, например 20) для того же проекта. Реализуется в `JobQueue._schedule`:
   не переключаться, если с последней задачи текущей модели прошло < N сек.
2. **Защита от голодания.** Строгое правило I6 означает: если проект непрерывно грузит текущую
   модель, задачи к другим моделям истекут через `AIM_JOB_WAIT_TIMEOUT`. Если это станет
   проблемой — порог `AIM_SWITCH_STARVATION_SEC`: самая старая чужая задача ждёт дольше порога →
   новые задачи к текущей модели перестают выдаваться, и после завершения текущих — переключение.
3. **Приоритеты.** Колонка `priority` + сортировка ожидающих (интерактивные IDE выше ночного
   auto_posting).
4. **Прерывание генерации картинок.** OpenVINO GenAI поддерживает `callback` шага генерации
   (в установленной 2026.3 в docstring не указан — проверить); вернуть `True` по
   `ticket.stop_requested` → таймаут картинки освобождает GPU сразу.
5. **Токены в стриме.** Для `stream=true` usage не пишется в БД; можно извлекать из последнего
   чанка (`usage` при `stream_options.include_usage`, или `timings` llama-server).
6. **Простая страница очереди** (веб-интерфейс удалён в `1067e09`): таблица `GET /api/queue` +
   `GET /api/jobs` с кнопкой «Отменить».
7. Старые методы `ModelManager.chat/image/tts/text_backend_for` больше не вызываются эндпоинтами —
   можно удалить после проверки.

## 5. Справочник API (кратко)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/queue` | Выполняются / ждут, `switch_locked` |
| POST | `/api/jobs` | Async-задача (`kind`: chat/image/tts, `model`, `project`, `payload`, `wait_timeout`, `run_timeout`) → `202 {id}` |
| GET | `/api/jobs` | История (`status`, `project`, `model`, `limit`) |
| GET | `/api/jobs/stats` | Сводка за `hours` |
| GET | `/api/jobs/{id}` | Статус и результат |
| POST | `/api/jobs/{id}/cancel` | Отмена |

Коды ошибок очереди: `409 model_busy`, `409 queue_busy`, `503 expired`, `504 timeout`,
`499 cancelled`. Подробно — `SPEC.md`, раздел 4.5.
